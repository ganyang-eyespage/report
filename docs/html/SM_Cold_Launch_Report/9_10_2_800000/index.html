Final recommendation

建议采用实验 B：priority + singleton，max_request=40，per_host_max_request=40

单一全量配置结论

如果只能发一个实验配置，推荐 enable_priority_schedule=true、enable_singleton_okhttp=true、max_request=40、per_host_max_request=40。

按 device_performance_level + country + network 做同质分层匹配后，它在两个目标 API 上的 success_time P90 综合下降 -659 ms，P50 综合下降 -83 ms。

分层配置备选

如果远端配置允许按设备性能下发：device_performance_level > 0 用 40/40 + singleton；<=0 可考虑 60/40 + singleton，它在低/中性能设备的 new-feed P90 更靠前，但线程与同 host 并发压力更高。

为什么不是直接看裸 P90？裸 P90 会被设备性能、国家、网络结构影响。裸数据里 60/40 在配对样本上略优，但分层匹配后 40/40 对两条 API 的综合 P90 收益最大。
为什么不是 32/20？32/20 在低/中性能设备、异常裁剪口径下有收益，但全量分层匹配的 P90 收益明显低于 singleton 组合；高性能设备上 32/20 no singleton 还会落后控制组。
本实验不能解决什么？现有业务链路仍是 get-tab-config 返回后才创建首屏 feed Fragment 并触发 new-feed；配置只能压队列/连接/并发造成的尾部，不能消除这段串行等待。

Experiment groups and metric definition

实验口径

指标解释

  • success_time：从 App 启动计时到目标 API 成功时刻，是本报告主指标。
  • start_loading_time：从 App 启动计时到目标 API 开始 loading/请求时刻，用来判断业务链路是否延迟发请求。
  • request duration：success_time - start_loading_time，近似目标请求自身耗时。
  • 异常裁剪：沿用旧报告思路，start_loading_time > 10000ms 或 success_time > 30000ms 作为异常尾部单独观察。

为什么用分层匹配

不同实验组的设备性能、国家、网络结构并不完全一致；直接比较裸 P90 会把“样本结构差异”误当作“配置效果”。本报告以 device_performance_level + country + network 为 cell，要求控制组和实验组每个 cell 都至少 80 条样本，然后按 min(n_control, n_exp) 加权平均差值。

Request chain limit

业务串行链路限制了本实验的收益上限

同一次启动内配对 uid + start_app_count，new-feed 仍稳定晚于 get-tab-config。配置优化能改善队列和连接竞争，但不会改变“先拿 tab 配置，再创建首屏 feed 并请求 new-feed”的链路。
