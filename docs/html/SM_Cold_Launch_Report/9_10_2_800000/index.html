总览结论

主结论不变

如果以冷启最终可见收益为目标，主指标仍应看 success_time。分层匹配综合两个 API 后，推荐 实验 B：priority + singleton，40/40，success P90 综合下降约 -659 ms。

新增 start 口径结论

如果只看 /feed/get-tab-config 的 start_loading_time，裸数据里 60/40 最小；但按设备性能 + 国家 + 网络分层匹配后，40/40 + singleton 仍是更稳的全量建议。

tab_config start_loading_time 越小越好：专项结论

这个口径衡量的是 tab_config 请求是否更早开始，不直接代表页面最终完成，但它能反映调度/连接复用是否让首个关键 API 更早进入请求阶段。

建议：全量统一配置仍用 40/40 + singleton。裸数据中 60/40 的 tab_config start P90 为 7,523 ms，40/40 为 7,651 ms，60/40 快约 128 ms；但分层匹配后 40/40 的 start P90 相对控制组下降 -416 ms，优于 60/40，且并发风险更低。

singleton 运行态OkHttpScheduleHelper.kt:37低/中性能设备会因 shouldUseSingletonClient() 强制走 singleton client。
埋点字段OkHttpScheduleHelper.kt:44start/success 外，补充 is_enable、max_request、per_host、use_singleton_client、target_api。
URGENT 白名单PriorityPathConfig.kt:12get-tab-config 和 new-feed 都已经在 URGENT 列表中。
调度接入BaseHttpClient.kt:161,241优先级开启后使用 PriorityDispatcher，并在 enqueue 前通过 PriorityTagCallFactory 打 tag。
业务链路HomePartyTabSquareFragment.kt:537 + PartySquareFeedFragment.kt:373先请求 tab_config，再创建首屏 feed Fragment 触发 new-feed。

最终建议

全量统一配置

{
  "enable_priority_schedule": true,
  "enable_singleton_okhttp": true,
  "max_request": 40,
  "per_host_max_request": 40
}

灰度观察项

  • 主看 success_time P50/P90/P95，辅看 tab_config start_loading_time。
  • 观察失败率、超时率、线程数、CPU、ANR，以及 urgent_expand/shrink 是否异常频繁。
  • 如低端机单独下发，比较 32/20 与 60/40，避免直接全量推高到 60/40。
